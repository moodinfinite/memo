## Issue 1 — API endpoints are unauthenticated (HIGH)

**Problem:** All three serverless API handlers (`api/generate-story.ts`, `api/review-sentence.ts`, `api/lookup-word.ts`) accept requests from anyone. The client sends a Bearer JWT token in the `authorization` header, but the server never reads or validates it.

**Why it matters:** Anyone who discovers the endpoint URLs can call them without logging in, burning Anthropic API credits. The endpoints are visible in the browser's network tab.

**Fix:** Add a Supabase JWT verification step at the top of each handler, before the rate-limit check:
```ts
import { createClient } from '@supabase/supabase-js'

const token = (req.headers['authorization'] as string)?.replace('Bearer ', '')
const supabase = createClient(process.env.SUPABASE_URL!, process.env.SUPABASE_ANON_KEY!)
const { data: { user }, error } = await supabase.auth.getUser(token)
if (!user || error) return res.status(401).json({ error: 'Unauthorized' })
```

## Issue 2 — In-memory rate limiting doesn't work on serverless (MEDIUM)

**Problem:** Each API file holds a module-level `rateLimitMap`. On Vercel, each serverless function invocation may run in a fresh isolated process, so the map starts empty every cold start. A determined caller can bypass the limit by triggering cold starts (e.g. waiting 60 seconds between bursts) or by hitting different instances simultaneously.

**Why it matters:** The rate limit is the only abuse protection today (given Issue 1 is unresolved). It provides false confidence — it works locally but not in production.

**Fix (short-term):** Once auth is added (Issue 1), the JWT ties each request to a known user, making abuse traceable and blockable. That alone substantially reduces risk.

**Fix (long-term):** Use Vercel KV or Upstash Redis for a shared counter keyed by `user_id`, rather than an in-memory map keyed by IP.

## Issue 3 — `_lastPersistArgs` stored as untyped side-channel (LOW)

**Problem:** `studyStore.ts` stores retry args by mutating the Zustand state object directly:
```ts
;(get() as any)._lastPersistArgs = [known, unknown, total, mode, setId, clearDraft]
```
This bypasses TypeScript (the property isn't in `StudyState`) and is never cleared by `resetSession()` or `startLearnSession()`. If `retryPersist` is called before any `_persist` has run in the current session, `_lastPersistArgs` could hold stale data from a previous session.

**Why it matters:** Low risk day-to-day, but it's a silent footgun — the TypeScript compiler won't catch a bug here, and the retry could silently double-insert a prior session's stats into `study_sessions`.

**Fix:** Declare the field properly in the interface and clear it in `resetSession`:
```ts
// in StudyState interface:
_lastPersistArgs: Parameters<StudyState['_persist']> | null

// in resetSession:
set({ ..., _lastPersistArgs: null })
```
